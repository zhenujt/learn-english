# Software Workplace Grammar: A Progressive Guide

> A practical grammar system for the 100 sentence cards, software demos, meetings, status updates, bug discussions, code reviews, and technical decisions.

## 1. How to Use This Guide

Grammar is useful only when it helps you complete a communication task. Do not try to memorize every rule at once. Study the guide in five stages:

1. Build a complete short sentence.
2. Put the action in the correct time.
3. Ask, request, and clarify politely.
4. Connect ideas with reasons, conditions, and contrasts.
5. Combine short sentences into a clear workplace explanation.

For every pattern, use the same four-step drill:

```text
Recognize -> Recall -> Replace -> Connect
```

- **Recognize:** Understand the sentence when you see or hear it.
- **Recall:** Produce it from the Chinese meaning.
- **Replace:** Change the feature, action, date, person, or result.
- **Connect:** Use it with two or three other patterns in a real explanation.

Complete every exercise set with the same method:

1. Keep the answers closed and work without checking the lesson.
2. Say speaking answers aloud and write writing answers as complete sentences.
3. Open the reference answers only after finishing the entire set.
4. Repeat incorrect items one day later. Scenario tasks may have multiple correct answers.

Reach 80% before moving to the next level. Below 80%, review only the sections connected to your errors and try the set again.

The goal is not grammatical complexity. The goal is accurate, reusable speech under pressure.

### Start Here If You Know Only a Few Words

If terms such as *subject*, *verb*, and *past participle* are unfamiliar, complete the **Zero-Basis Preparation** below before reading the numbered levels. Then study only Sections 3, 4.1, 5.1–5.3, and 6.1. Continue when you can pass the first checkpoint.

On your first pass, you may:

- Read the Chinese translation.
- Imitate a pattern before you can explain every word.
- Return to the terminology table whenever necessary.
- Speak short sentences instead of long ones.
- Study one small section for 15–25 minutes per day.

Do not try to learn grammar, every new word, and pronunciation at the same time. First understand the message, then listen and repeat, and finally replace one word.

## Zero-Basis Preparation: Learn to Read One Sentence

### Preparation 1: Words Have Jobs

You initially need only five roles:

| Role | Job | Software examples |
|---|---|---|
| Noun | Names a person, thing, or idea | `user`, `page`, `issue`, `code` |
| Pronoun | Replaces a noun | `I`, `you`, `we`, `it`, `they` |
| Verb | Shows an action or state | `open`, `test`, `need`, `is` |
| Adjective | Describes a person or thing | `ready`, `slow`, `clear` |
| Preposition | Shows time, place, or relation | `in`, `on`, `before`, `with` |

```text
We       review       the code.
who      does what     receives the action
subject  verb          object
```

A *subject* is who or what the sentence is about. A *predicate* says what the subject does or what state it is in. An *object* receives the action. Understand these questions before memorizing the terms.

### Preparation 2: The Most Useful Subjects

| English | Basic pairing |
|---|---|
| I | `I am`, `I work` |
| you | `you are`, `you work` |
| we | `we are`, `we work` |
| they | `they are`, `they work` |
| he / she | `he is`, `she works` |
| it | `it is`, `it works` |

Begin with `I`, `we`, and `it`:

```text
I am ready.
We need time.
It works.
```

### Preparation 3: What Is `be`?

`Am`, `is`, and `are` are present forms of `be`. They connect a subject to its identity, state, or location.

```text
I am ready.
The page is slow.
The tests are complete.
```

Memorize one line:

```text
I am | you/we/they are | he/she/it is
```

Add `not` for a negative. Move `be` before the subject for a question:

```text
The feature is ready.
The feature is not ready.
Is the feature ready?
```

### Preparation 4: Ordinary Action Sentences

Do not add `am/is/are` before an ordinary base verb:

```text
I review the code.
We test the feature.
The page shows an error.

Wrong: I am review the code.
Right: I review the code.
```

Learn these verbs as phrases:

| Verb | Minimum phrase |
|---|---|
| open | open the page |
| close | close the dialog |
| click | click the button |
| show | show the result |
| need | need more time |
| check | check the logs |
| test | test the fix |
| review | review the code |
| fix | fix the issue |
| deploy | deploy the release |

### Preparation 5: One, the One, and More Than One

- `a/an` introduces one thing: `a bug`, `an error`.
- `the` points to the thing both people know: `the bug`, `the page`.
- A plural countable noun normally takes `-s`: `one user`, `two users`.

```text
There is a bug.
The bug affects users.
There are two errors.
```

Beginners do not need perfect article use, but should notice that a singular countable noun normally needs a determiner.

### Preparation 6: Why Verbs Change

Recognize these forms before trying to memorize every rule:

| Name | Form | Example |
|---|---|---|
| Base form | `test` | `We test it.` / `We can test it.` |
| Third-person singular | `tests` | `QA tests it.` |
| Past form | `tested` | `QA tested it yesterday.` |
| Past participle | `tested` | `QA has tested it.` |
| `-ing` form | `testing` | `QA is testing it.` |

Some verbs are irregular:

```text
go -> went -> gone
do -> did -> done
write -> wrote -> written
```

The *base form* is the dictionary form, such as `review`, rather than `reviews`, `reviewed`, or `reviewing`.

### Preparation 7: Read from Left to Right in Chunks

Do not translate a long sentence word by word. Divide it by meaning:

```text
We need / to test the fix / before release.
who      / action          / time
```

Ask:

1. Who or what? `We`
2. What action or state? `need`
3. What extra information? `to test the fix before release`

For `Could you / review this pull request / today?`, first learn `Could you...?` as one polite-request block.

### Preparation 8: Your First Drill

Keep the answers closed. Write or say each complete English sentence:

1. Say that the feature is ready.
2. Say that you are testing the fix.
3. Say that your team needs more time.
4. Ask someone to check the logs.
5. Promise to finish something by Friday.
6. Make `The feature is ready.` negative.
7. Turn `The feature is ready.` into a yes/no question.
8. Is `We test the feature.` a state sentence or an action sentence?
9. Replace `code` with `pull request` in `We review the code.`
10. Use `There is` to report an error in the console.

<details>
<summary>Show reference answers</summary>

1. `The feature is ready.`
2. `I am testing the fix.`
3. `We need more time.`
4. `Can you check the logs?`
5. `I will finish it by Friday.`
6. `The feature is not ready.` Add `not` after `is`.
7. `Is the feature ready?` Move `is` before the subject.
8. It is an action sentence. Its main verb is `test`.
9. `We review the pull request.`

First checkpoint:

- Distinguish a state sentence, `The feature is ready`, from an action sentence, `We test the feature`.
- Use `I am`, `it is`, and `we are`.
- Produce one statement, one negative, and one simple question.
- Replace `feature` with `page`, `API`, or `release`.

If you cannot do these yet, repeat Preparations 2–8. You do not need present perfect or clauses yet.

## 2. What the 100 Cards Cover

| Group | Main communication task |

| Requirements and product | Confirm expected behavior and scope |
| Technical discussion | Explain approaches, dependencies, and trade-offs |
| Code and pull requests | Request reviews and discuss code changes |
| Testing and bugs | Reproduce issues and compare actual and expected results |
| Demo, release, and production | Demonstrate behavior and discuss deployment |
| Opinions, decisions, and follow-up | Agree, disagree, recommend, and record actions |

## 3. Level One: Build the Sentence Skeleton

### 3.1 Subject + verb

Use this pattern for actions and events that do not need an object.

```text
The build failed.
The dialog opens.
Testing continues.
```

Ask two questions:

1. Who or what is the sentence about?
2. What happens?

Common mistake:

```text
Wrong: The build failure.
Right: The build failed.
```

`Failure` is a noun. A complete sentence normally needs a verb such as `failed`.

### 3.2 Subject + be + description

Use `be` to describe identity, state, location, or progress.

```text
The feature is ready.
The API is backward-compatible.
The issue is in production.
Testing is in progress.
```

Choose the correct form:

| Subject | Present | Past |
|---|---|---|
| I | am | was |
| he, she, it, singular noun | is | was |
| you, we, they, plural noun | are | were |

Common mistake:

```text
Wrong: The tests is complete.
Right: The tests are complete.
```

### 3.3 Subject + verb + object

Use this pattern when an action affects something.

```text
We need more information.
I updated the documentation.
QA verified the fix.
The page shows an error message.
```

Learn verbs together with their usual objects:

```text
review a pull request
deploy a release
reproduce an issue
update the documentation
meet a deadline
raise a concern
```

### 3.4 Subject + modal + base verb

A modal verb is followed by the base form of the main verb.

```text
We can deploy today.
We should add more logging.
I will review the pull request.
The change might affect performance.
```

Common mistake:

```text
Wrong: We should to add more logging.
Right: We should add more logging.

Wrong: She can reviews it today.
Right: She can review it today.
```

### 3.5 There is / there are

This pattern is not a major focus of the 100 cards, but it is highly useful for software communication.

```text
There is an error in the console.
There are two open questions.
There was a timeout during deployment.
```

Use `there is` with a singular or uncountable noun and `there are` with plural nouns.

### Level One Exercises: Sentence Skeletons

1. Complete: `The page ___ slow.`
2. Correct: `The tests is complete.`
3. Correct: `I am review the pull request.`
4. Report that the build failed.
5. Say that your team needs more information.
6. Use `can` to say that your team can deploy today.
7. Use `There are` to report two open questions.
8. Scenario: Use three short sentences to report that the feature is ready, QA is testing, and one blocker exists.

<details>
<summary>Show Level One answers</summary>

1. `The page is slow.` The subject is singular, so use `is`.
2. `The tests are complete.` `Tests` is plural.
3. `I review the pull request.` An ordinary action does not use `am + base verb`.
4. `The build failed.`
5. `We need more information.`
6. `We can deploy today.` A modal is followed by the base verb.
7. `There are two open questions.`
8. Sample: `The feature is ready. QA is testing it. There is one blocker.`

</details>

## 4. Level Two: Put Work in Time

### 4.1 Present simple: facts, states, and repeatable behavior

Formula:

```text
I/You/We/They + base verb
He/She/It + verb-s
```

Use it for:

- Current facts: `The service depends on Redis.`
- Product behavior: `The page refreshes automatically.`
- Repeatable bugs: `The issue happens when users refresh the page.`
- Opinions: `I think this approach is simpler.`
- Demo narration: `I click Save, and the dialog closes.`

Negatives and questions require `do` or `does`:

```text
The API does not support pagination.
Does this change affect existing users?
Why does the request fail?
```

Common mistake:

```text
Wrong: Why the request fails?
Right: Why does the request fail?
```

### 4.2 Present continuous: work in progress or temporary activity

Formula:

```text
am/is/are + verb-ing
```

```text
I am investigating the issue.
We are testing the fix in staging.
The team is working on the migration.
```

Contrast:

```text
I test the release every Friday.      repeatable routine
I am testing the release now.         activity in progress
```

Some state verbs are not normally continuous:

```text
Wrong: I am understanding the problem.
Right: I understand the problem.
```

### 4.3 Past simple: finished events

Formula:

```text
subject + past form
did not + base verb
Did + subject + base verb ...?
```

```text
The deployment failed last night.
I reproduced the issue locally.
We did not change the API contract.
When did the issue start?
```

Common mistake:

```text
Wrong: When did it started?
Right: When did it start?
```

After `did`, use the base form.

### 4.4 Present perfect: past work connected to now

Formula:

```text
have/has + past participle
```

```text
We have completed the implementation.
Has the fix been tested?
I have not reviewed the pull request yet.
```

Use present perfect when the current result matters or the exact past time is not important. Use past simple with a finished time:

```text
We have deployed the fix.             current result
We deployed the fix yesterday.        finished past time
```

Useful markers:

```text
already, yet, just, so far, since, for
```

### 4.5 Future forms: plans, promises, and predictions

Use `will` for a decision, promise, or prediction:

```text
I will review it today.
The migration will take two days.
```

Use `be going to` for an existing intention or visible evidence:

```text
We are going to deploy after lunch.
```

Use present continuous for an arranged plan:

```text
We are meeting the product team tomorrow.
```

For a deadline, use `by`:

```text
We will finish it by Friday.
```

`By Friday` means no later than Friday. `On Friday` means the event happens on Friday.

### Level Two Exercises: Time and Tense

1. Choose and explain: for tests run every day, use `We run` or `We are running`?
2. Say that you are investigating the issue now.
3. Report that the deployment failed last night.
4. Correct: `When did the issue started?`
5. Say that your team has deployed the fix, emphasizing the current result.
6. Choose and explain: with `yesterday`, use `have completed` or `completed`?
7. Promise to finish something by Friday.
8. Scenario: Use three sentences to report that development finished yesterday, testing is happening now, and deployment is tomorrow.

<details>
<summary>Show Level Two answers</summary>

1. `We run the tests every day.` Use present simple for repeated behavior.
2. `I am investigating the issue now.`
3. `The deployment failed last night.`
4. `When did the issue start?` Use the base verb after `did`.
5. `We have deployed the fix.`
6. `We completed it yesterday.` A specific finished time normally takes past simple.
7. `We will finish it by Friday.` `By` means no later than that time.
8. Sample: `We completed the implementation yesterday. We are testing it now. We will deploy it tomorrow.`

</details>

## 5. Level Three: Ask Useful Questions

### 5.1 Be questions

Move `be` before the subject:

```text
The feature is ready. -> Is the feature ready?
Customers are affected. -> Are customers affected?
```

### 5.2 Do/does/did questions

Use these when the main verb is not `be` and there is no modal:

```text
Does this meet the requirement?
Do we need another review?
Did the deployment succeed?
```

### 5.3 Modal questions

Move the modal before the subject:

```text
Can we deploy today?
Could you review this pull request?
Should we add a fallback?
Will this affect existing users?
```

### 5.4 Wh- questions

Core formula:

```text
question word + auxiliary/modal + subject + main verb ...?
```

```text
What does this endpoint return?
Why did the build fail?
When can we deploy?
How should we handle this case?
Which environment are you using?
Who owns this task?
```

When the question word itself is the subject, do not add `do`:

```text
What caused the issue?
Who approved the change?
```

### 5.5 Indirect questions

Indirect questions sound calmer and more professional. After the opening phrase, use statement word order.

```text
Direct: When will the fix be ready?
Indirect: Could you confirm when the fix will be ready?

Direct: Why did the request fail?
Indirect: Do we know why the request failed?
```

Common mistake:

```text
Wrong: Could you tell me when will it be ready?
Right: Could you tell me when it will be ready?
```

### Level Three Exercises: Asking Questions

1. Turn `The feature is ready.` into a yes/no question.
2. Turn `This meets the requirement.` into a yes/no question.
3. Turn `The deployment succeeded.` into a yes/no question.
4. Ask about the reason in `The request failed because the token expired.`
5. Ask when your team can deploy.
6. Correct: `Why the API is slow?`
7. Correct: `Could you tell me when will it be ready?`
8. Scenario: Ask about the reason, time, and owner of a failed build.

<details>
<summary>Show Level Three answers</summary>

1. `Is the feature ready?`
2. `Does this meet the requirement?` Use `meet` after `does`.
3. `Did the deployment succeed?` Use `succeed` after `did`.
4. `Why did the request fail?`
5. `When can we deploy?`
6. `Why is the API slow?` Move `be` before the subject.
7. `Could you tell me when it will be ready?` The indirect question uses statement order.
8. Sample: `Why did the build fail? When did it fail? Who owns the investigation?`

</details>

## 6. Level Four: Requests, Ability, Advice, and Certainty

### 6.1 Can and could

```text
Can we move on to the next topic?      permission or possibility
Can you share your screen?             direct request
Could you repeat that, please?         more polite request
```

`Could` often makes a request softer; it does not necessarily refer to past time.

### 6.2 Should

Use `should` for advice, expected behavior, or a recommended action.

```text
We should add more logging.
The user should see a clear error message.
```

### 6.3 Must, have to, and need to

```text
We must fix the security issue before release.       strong requirement
We have to update the dependency.                    external necessity
We need to confirm the expected behavior.            practical need
```

Important distinction:

```text
You must not deploy this build.       deployment is prohibited
You do not have to deploy today.      deployment is not necessary
```

### 6.4 May, might, and could

Use these for uncertainty and risk:

```text
This may affect performance.
The change might break older clients.
The timeout could be caused by the database.
```

A useful certainty scale is:

```text
will -> probably will -> may/might/could -> probably will not -> will not
```

### 6.5 Would

Use `would` for polite requests, preferences, and hypothetical results:

```text
Would you mind checking the logs?
I would prefer the simpler option.
That would reduce the deployment risk.
```

### Level Four Exercises: Requests, Advice, and Certainty

1. Use `could` to politely ask someone to repeat something.
2. Use `should` to recommend more logging.
3. Say that the security issue must be fixed before release.
4. Explain the difference between `must not deploy` and `do not have to deploy`.
5. Use `might` to say that the change could break older clients.
6. Use `would prefer` to favor the simpler option.
7. Correct: `We should to add a fallback.`
8. Scenario: Politely ask a colleague to review a pull request today and say it may affect the release.

<details>
<summary>Show Level Four answers</summary>

1. `Could you repeat that, please?`
2. `We should add more logging.`
3. `We must fix the security issue before release.`
4. `Must not deploy` prohibits deployment; `do not have to deploy` says deployment is unnecessary.
5. `The change might break older clients.`
6. `I would prefer the simpler option.`
7. `We should add a fallback.` Do not add `to` after a modal.
8. Sample: `Could you review the pull request today? It might affect the release.`

</details>

## 7. Level Five: Describe Actions Precisely

### 7.1 To-infinitives

Common patterns:

```text
need to test
plan to deploy
want to confirm
ask someone to review
allow users to export data
```

```text
We need to finish testing.
This allows users to reset their passwords.
I asked QA to verify the fix.
```

### 7.2 Gerunds

A gerund is an `-ing` form used like a noun.

```text
Testing is still in progress.
We discussed adding a cache.
This prevents users from submitting the form twice.
```

Common combinations:

```text
finish testing
avoid breaking
consider using
suggest adding
prevent someone from doing
```

### 7.3 Participles as descriptions

```text
a breaking change
the affected users
the expected result
the updated component
```

`-ing` often describes the cause or active quality; `-ed` often describes the affected thing or completed state.

```text
The behavior is confusing.        it causes confusion
The user is confused.             the user feels confusion
```

### Level Five Exercises: Describing Actions Precisely

1. Complete: `We need ___ (finish) testing.`
2. Complete: `We discussed ___ (add) a cache.`
3. Correct: `This prevents users to submit twice.`
4. Say that you asked QA to verify the fix.
5. Choose `confusing` or `confused`: `The user is ___.`
6. Scenario: Make one technical-plan sentence with each of `plan to`, `consider using`, and `avoid breaking`.

<details>
<summary>Show Level Five answers</summary>

1. `We need to finish testing.` `Need` commonly takes an infinitive.
2. `We discussed adding a cache.` `Discuss` takes a gerund.
3. `This prevents users from submitting twice.` Use `prevent someone from doing`.
4. `I asked QA to verify the fix.`
5. `The user is confused.` The user receives the effect.
6. Sample: `We plan to deploy tonight. We are considering using a cache. We want to avoid breaking older clients.`

</details>

## 8. Level Six: Passive Voice

> **Beginner pause point:** Skip Sections 8–11 on your first pass. Return after you can comfortably talk about present routines, current work, past events, and future plans.

Formula:

```text
be + past participle
```

Use the passive when the result, process, or affected object matters more than the actor.

```text
The fix has been tested.
The issue was caused by stale cache data.
Only a small number of users are affected.
The release will be deployed tonight.
```

Tense remains on `be`:

| Time | Active | Passive |
|---|---|---|
| Present | QA tests the fix. | The fix is tested. |
| Past | QA tested the fix. | The fix was tested. |
| Present perfect | QA has tested the fix. | The fix has been tested. |
| Future | QA will test the fix. | The fix will be tested. |

Do not use the passive merely to sound formal. Prefer active voice when ownership matters:

```text
Clear ownership: I will update the API documentation.
Useful focus: The documentation will be updated before release.
```

### Level Six Exercises: Passive Voice

1. Make passive: `QA tested the fix.`
2. Make passive: `QA has tested the fix.`
3. Make passive: `The team will deploy the release tonight.`
4. Report that only a small number of users are affected.
5. Choose active or passive and explain: the listener needs to know who will update the documentation.
6. Scenario: Use passive voice to report the issue cause, fix test status, and deployment time.

<details>
<summary>Show Level Six answers</summary>

1. `The fix was tested by QA.`
2. `The fix has been tested by QA.`
3. `The release will be deployed tonight.`
4. `Only a small number of users are affected.`
5. Active is clearer: `I will update the documentation.` The owner matters.
6. Sample: `The issue was caused by stale cache data. The fix has been tested. It will be deployed tonight.`

</details>

## 9. Level Seven: Connect Ideas

### 9.1 Addition and contrast

```text
The implementation is complete, and testing is in progress.
The approach is simple, but it requires a schema change.
The first option is faster, while the second is safer.
```

### 9.2 Reason and result

```text
We chose this approach because it is easier to maintain.
The token expired, so the request failed.
Since this is a breaking change, we need a migration plan.
Therefore, I recommend delaying the release.
```

Use `because` before a reason and `so` before a result. Avoid using both for the same relationship in one sentence.

```text
Awkward: Because the token expired, so the request failed.
Right: Because the token expired, the request failed.
Right: The token expired, so the request failed.
```

### 9.3 Time clauses

```text
When users refresh the page, the session expires.
Before we deploy, we need to run the regression tests.
After the migration finishes, we will verify the data.
While QA is testing the fix, I will update the documentation.
```

For future time clauses, normally use present simple after `when`, `before`, and `after`:

```text
Wrong: When the migration will finish, we will verify the data.
Right: When the migration finishes, we will verify the data.
```

### 9.4 Relative clauses

Use a relative clause to identify or describe a noun.

```text
The component that handles authentication is shared.
The users who reported the issue are enterprise customers.
The release, which includes the security fix, is ready.
```

- `who` refers to people.
- `that` or `which` refers to things.
- Commas mark extra, nonessential information.

### 9.5 Noun clauses

A noun clause can serve as the object of `know`, `think`, `confirm`, `explain`, or `understand`.

```text
We need to confirm what the expected behavior is.
I think that the cache is stale.
Could you explain why this change is necessary?
We do not know whether the issue affects all users.
```

Use statement word order inside the clause:

```text
Wrong: We need to confirm what is the expected behavior.
Right: We need to confirm what the expected behavior is.
```

### Level Seven Exercises: Connecting Ideas

1. Use `but`: the approach is simple; it requires a schema change.
2. Use `because`: your team chose the approach; it is easier to maintain.
3. Correct: `Because the token expired, so the request failed.`
4. Complete: `Before we ___ (deploy), we need to run the tests.`
5. Use a relative clause to identify the component that handles authentication.
6. Correct: `We need to confirm what is the expected behavior.`
7. Use `whether` to say you do not know if the issue affects all users.
8. Scenario: Use a reason, a contrast, and a next step to explain a failed request.

<details>
<summary>Show Level Seven answers</summary>

1. `The approach is simple, but it requires a schema change.`
2. `We chose this approach because it is easier to maintain.`
3. `Because the token expired, the request failed.` or `The token expired, so the request failed.`
4. `Before we deploy, we need to run the tests.` Use present simple in the future time clause.
5. `The component that handles authentication is shared.`
6. `We need to confirm what the expected behavior is.` Use statement order inside the clause.
7. `We do not know whether the issue affects all users.`
8. Sample: `The request failed because the token expired. The API returned 401, but the page showed no message. Therefore, we will add error handling.`

</details>

## 10. Level Eight: Conditions and Hypotheses

### 10.1 Zero conditional: stable behavior

```text
If the token expires, the API returns 401.
```

Formula:

```text
if + present simple, present simple
```

Use it for system behavior, rules, and repeatable results.

### 10.2 First conditional: realistic future possibility

```text
If the tests pass, we will deploy tonight.
If it fails again, we can roll back the release.
```

Formula:

```text
if + present simple, will/can/may + base verb
```

Do not normally use `will` in the `if` clause:

```text
Wrong: If the tests will pass, we will deploy.
Right: If the tests pass, we will deploy.
```

### 10.3 Second conditional: hypothetical design choices

```text
If we moved this logic to the backend, the client would be simpler.
If we had more time, I would add integration tests.
```

Formula:

```text
if + past simple, would + base verb
```

This structure is especially useful in architecture and trade-off discussions.

### 10.4 Unless and otherwise

```text
We cannot release unless the critical tests pass.
We need to update the schema; otherwise, the migration will fail.
```

`Unless` means `if not`.

2. Describe a real plan: your team will deploy tonight if the tests pass.
3. Correct: `If the tests will pass, we will deploy.`
4. Describe a hypothetical choice: moving the logic to the backend would make the client simpler.
5. Use `unless` to say release is impossible before the critical tests pass.
6. Use `otherwise` to say the migration will fail without a schema update.

1. `If the token expires, the API returns 401.`
2. `If the tests pass, we will deploy tonight.`
3. `If the tests pass, we will deploy.` Do not normally use `will` in the `if` clause.

## 11. Level Nine: Compare Options and Express Opinions

### 11.1 Comparatives

```text
This approach is simpler.
The cached version is faster than the original version.
Option A is more flexible but less predictable.
```

Common forms:

```text
fast -> faster
simple -> simpler
easy -> easier
reliable -> more reliable
complex -> less complex
```

### 11.2 Balanced trade-offs

```text
Option A is faster, but it uses more memory.
Option B is easier to maintain, although it requires more initial work.
The benefit is lower latency; the trade-off is additional complexity.
```

### 11.3 Agreement and disagreement

```text
I agree with that approach.
That makes sense to me.
I agree with the goal, but I am concerned about the timeline.
I see your point. However, this may affect backward compatibility.
I would recommend a smaller change first.
```

Prefer `I think`, `I suggest`, `I recommend`, and `I am concerned` over absolute claims when discussing uncertain decisions.

## 12. Level Ten: Build Complete Workplace Explanations

### 12.1 Demo chain

```text
Context -> Goal -> Action -> Result -> Value -> Transition
```

```text
This is the user management page.
It allows administrators to manage team members.
First, I click Add user.
A dialog opens, and I enter the user's details.
After I click Save, the new user appears in the table.
This reduces the number of steps required to onboard a teammate.
Next, let's look at filtering.
```

Main grammar:

- Present simple for visible behavior.
- `can` and `allow someone to` for capability.
- Time clauses for action and result.
- Connectors for sequence.

### 12.2 Bug chain

```text
Problem -> Steps -> Actual -> Expected -> Impact -> Next step
```

```text
Users cannot submit the form after their session expires.
The issue happens when they leave the page open for more than an hour.
When they click Submit, the API returns 401, but the page shows no message.
The page should ask them to sign in again.
This blocks users from completing the workflow.
I am adding error handling, and QA will test the fix this afternoon.
```

Main grammar:

- Present simple for repeatable behavior.
- `when` for reproduction conditions.
- `should` for expected behavior.
- Present continuous and future forms for the fix plan.

### 12.3 Status chain

```text
Completed -> Current -> Blocker -> ETA -> Next step
```

```text
I have completed the implementation.
I am testing the migration in staging now.
The only blocker is access to the production snapshot.
If I get access today, I will finish by Thursday.
After that, I will open the pull request.
```

### 12.4 Technical-decision chain

```text
Recommendation -> Reason -> Trade-off -> Risk -> Mitigation
```

```text
I recommend using the existing authentication service.
The main reason is that it already supports token refresh.
It is easier to integrate, but we will have less control over caching.
The biggest risk is additional latency.
We can mitigate that by caching the public keys locally.
```

1. Demo: Introduce a page, perform an action, explain the result, and state the value.
2. Bug: Explain the trigger, actual result, expected result, and next step.
3. Status: Report completed work, current work, a blocker, and an ETA.
4. Technical decision: Give a recommendation, reason, trade-off, risk, and mitigation.

2. `The issue happens when the session expires. The API returns 401, but the page shows no message. The page should ask the user to sign in again. I am adding error handling now.`

### Weeks 1–2: Word roles and complete short sentences

Focus:

### Weeks 3–4: Present simple and basic questions

Focus:

### Weeks 5–6: Time and progress

- Past simple.

### Weeks 7–8: Completed work and polite collaboration

### Weeks 9–10: Connected reasoning

- Passive voice.

### Weeks 11–12: Full workplace routines

- Demo chain.
- Bug chain.
- Status chain.
- Technical-decision chain.

## 14. The Replacement Method

Take one sentence skeleton and replace one slot at a time:

```text
Could you review [the pull request] by [Friday]?
Could you review [the API design] by [tomorrow morning]?
Could you review [the migration plan] before [the meeting]?
```

Then change the grammar while keeping the content:

```text
I review the pull request every morning.         routine
I am reviewing the pull request now.             current action
I reviewed the pull request yesterday.           finished past action
I have reviewed the pull request.                current result
I will review the pull request after lunch.      future action
```

Finally, connect it:

```text
I have reviewed the pull request. The implementation looks good, but I found one backward-compatibility issue. If we fix that issue, we can merge it today.
```

## 15. Common Errors for Chinese Speakers

### Missing verbs

```text
Wrong: The feature very useful.
Right: The feature is very useful.
```

### Missing third-person `-s`

```text
Wrong: The page show an error.
Right: The page shows an error.
```

### Double past marking

```text
Wrong: Did the build failed?
Right: Did the build fail?
```

### Incorrect question order

```text
Wrong: Why the API is slow?
Right: Why is the API slow?
```

### Using an adjective as a verb

```text
Wrong: We need compatible the old API.
Right: We need to keep the old API compatible.
```

### Confusing `finish` and `finished`

```text
I finished the task.       past-tense verb
The task is finished.      completed state
```

### Translating “有” only as `have`

```text
Wrong: The console has an error.
Better: There is an error in the console.
```

### Overusing long sentences

```text
Risky: Because the deployment failed and users could not log in so we rolled back and now we are checking the logs.

Clearer: The deployment failed, and users could not log in. We rolled it back. We are checking the logs now.
```

## 18. Graduation Standard

You have learned a pattern when you can:

1. Understand it without translating every word.
2. Produce it from a Chinese prompt within three seconds.
3. Replace at least three content slots correctly.
4. Change it into a question, negative, past, or future form.
5. Connect it to two other sentences in a real software scenario.

For practical fluency, use this final test:

- Give a 60-second feature demo.
- Give a 45-second status update.
- Explain a bug from reproduction to next step.
- Compare two technical options and recommend one.
- Answer one follow-up question you did not prepare for.

Short, accurate sentences are the foundation. Complexity should be added only when it makes the relationship between ideas clearer.
