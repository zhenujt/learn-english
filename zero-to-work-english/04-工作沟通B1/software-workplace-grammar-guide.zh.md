# 软件职场英语语法全解：从 100 句到举一反三（测试）

> 面向软件 Demo、会议、进度同步、Bug 讨论、代码评审和技术决策的渐进式语法学习系统。

## 1. 这份文档怎么学

语法的价值不是让你记住术语，而是帮助你完成真实沟通任务。不要一次背完所有规则，按照下面五层逐步学习：

1. 先说出完整、准确的短句。
2. 把动作放到正确的时间中。
3. 学会提问、请求和澄清。
4. 用原因、条件、转折连接观点。
5. 把短句组合成完整的工作表达。

每个句型都采用同一套四步练习：

```text
识别 Recognize → 回忆 Recall → 替换 Replace → 连接 Connect
```

- **识别：**看到或听到句子时能理解。
- **回忆：**只看中文能够说出英文。
- **替换：**能替换功能、动作、日期、负责人和结果。
- **连接：**能和另外两三个句型组成真实表达。

每组练习都按下面的方法完成：

1. 先合上或遮住答案，不查原文完成题目。
2. 口语题必须大声说，书写题必须完整写出句子。
3. 完成整组后再展开“参考答案”。
4. 做错的题隔一天重做；场景题允许存在多个正确答案。

正确率达到 80% 再进入下一层。低于 80% 时不需要重读整章，只复习错题对应的小节并重新作答。

目标不是说出复杂语法，而是在有压力的会议和 Demo 中仍然能够准确、灵活地表达。

### 零基础读者先看这里

如果你只认识一些单词，不知道“主语、谓语、过去分词”是什么意思，不要直接从头读到尾。先完成下面的**零基础预备篇**，然后只学习第 3、4.1、5.1、5.2、5.3 和 6.1 节。能够完成第一阶段检查后，再继续后面的内容。

第一次学习时允许：

- 看中文，不要求全英文理解。
- 把一个句型作为整体模仿，不要求立即解释每个词。
- 忘记术语时回到下面的术语表。
- 先说短句，不急着说复杂句。
- 一天只学习一个小节，每次 15–25 分钟。

不要同时背语法、所有生词和发音。推荐顺序是：先理解句子意思，再听和跟读，最后只替换一个词。

## 零基础预备篇：先学会看懂一个句子

### 预备 1：单词在句子里各有工作

现在只需要认识五种角色：

| 角色 | 它做什么 | 软件工作例子 |
|---|---|---|
| 名词 noun | 表示人、事物或概念 | `user`、`page`、`issue`、`code` |
| 代词 pronoun | 代替名词 | `I`、`you`、`we`、`it`、`they` |
| 动词 verb | 表示动作或状态 | `open`、`test`、`need`、`is` |
| 形容词 adjective | 描述人或事物 | `ready`、`slow`、`clear` |
| 介词 preposition | 表示时间、位置或关系 | `in`、`on`、`before`、`with` |

看下面的句子：

```text
We       review       the code.
谁       做什么        对什么做
主语     动词          宾语
我们     评审          代码
```

`主语`只是“这句话在说谁或什么”；`谓语`只是“主语做什么或处于什么状态”；`宾语`是“动作作用到谁或什么”。先理解这三个问题，不必死背术语。

### 预备 2：先认识最常用的主语

| 英文 | 中文 | 搭配提示 |
|---|---|---|
| I | 我 | `I am`、`I work` |
| you | 你、你们 | `you are`、`you work` |
| we | 我们 | `we are`、`we work` |
| they | 他们、它们 | `they are`、`they work` |
| he / she | 他 / 她 | `he is`、`she works` |
| it | 它、这件事 | `it is`、`it works` |

软件沟通里可以先大量使用 `I`、`we`、`it`：

```text
I am ready.       我准备好了。
We need time.     我们需要时间。
It works.         它可以正常工作。
```

### 预备 3：be 是什么

`am`、`is`、`are` 都是 `be` 的现在形式。它们常常相当于中文里的“是、处于”：

```text
I am ready.             我准备好了。
The page is slow.       页面很慢。
The tests are complete. 测试完成了。
```

只记住这一行：

```text
I am | you/we/they are | he/she/it is
```

否定时在后面加 `not`，提问时把 `be` 放到前面：

```text
The feature is ready.       功能准备好了。
The feature is not ready.   功能还没准备好。
Is the feature ready?       功能准备好了吗？
```

### 预备 4：普通动作句

普通动作不需要再加 `am/is/are`：

```text
I review the code.       我评审代码。
We test the feature.     我们测试功能。
The page shows an error. 页面显示错误。
```

常见错误：

```text
错误：I am review the code.
正确：I review the code.
```

先把下面十个动词作为整块记忆：

| 动词 | 中文 | 最小搭配 |
|---|---|---|
| open | 打开 | open the page |
| close | 关闭 | close the dialog |
| click | 点击 | click the button |
| show | 显示 | show the result |
| need | 需要 | need more time |
| check | 检查 | check the logs |
| test | 测试 | test the fix |
| review | 评审 | review the code |
| fix | 修复 | fix the issue |
| deploy | 部署 | deploy the release |

### 预备 5：一个、这个和多个

- `a/an` 表示第一次提到的“一个”：`a bug`、`an error`。
- `the` 表示双方知道的“这个”：`the bug`、`the page`。
- 多个可数事物通常加 `-s`：`one user`、`two users`。

```text
There is a bug.          有一个 Bug。
The bug affects users.   这个 Bug 影响用户。
There are two errors.    有两个错误。
```

零基础阶段不必追求冠词完全正确，但要逐步养成“单数可数名词前通常需要限定词”的意识。

### 预备 6：动词为什么会变形

先认识四种常见样子，不要求一次背完所有变化：

| 名称 | 样子 | 用途示例 |
|---|---|---|
| 原形 | `test` | `We test it.` / `We can test it.` |
| 第三人称单数 | `tests` | `QA tests it.` |
| 过去式 | `tested` | `QA tested it yesterday.` |
| 过去分词 | `tested` | `QA has tested it.` |
| `-ing` 形式 | `testing` | `QA is testing it.` |

不规则动词需要单独记，例如：

```text
go -> went -> gone
do -> did -> done
write -> wrote -> written
```

看到“动词原形”，只需理解为词典里的基本形式，例如 `review`，不是 `reviews`、`reviewed` 或 `reviewing`。

### 预备 7：从左到右拆句

遇到长句时，不要逐词翻译，先按意义分块：

```text
We need / to test the fix / before release.
我们需要 / 测试这个修复 / 在发布之前。
```

按三个问题阅读：

1. 谁或什么？`We`
2. 做什么或什么状态？`need`
3. 补充了什么？`to test the fix before release`

再看一个问句：

```text
Could you / review this pull request / today?
你可以 / 评审这个 PR / 今天吗？
```

先认出整块 `Could you...?` 表示礼貌请求，不要先分析每个词。

### 预备 8：零基础第一次练习

不要先看答案。请完整写出或说出英文：

2. 我正在测试这个修复。
3. 我们需要更多时间。
4. 你可以检查日志吗？
5. 我会在星期五之前完成它。
6. 把 `The feature is ready.` 改为否定句。
7. 把 `The feature is ready.` 改为一般疑问句。
8. 判断句型：`We test the feature.` 是状态句还是动作句？
9. 把 `We review the code.` 中的 `code` 替换为 `pull request`。
10. 用 `There is` 表达“控制台里有一个错误”。

## 2. 100 句覆盖了什么

100 张卡分为十类，每类 10 张：

| 类别 | 主要沟通任务 |
|---|---|
| 会议基础表达 | 开始、过渡、补充、总结和结束 |
| 没听清与请求澄清 | 请求重复、放慢速度或换一种方式解释 |
| 工作与进度 | 描述状态、已完成工作和阻塞项 |
| 任务、截止日期与优先级 | 分配任务、确认优先级和讨论时间 |
| 需求与产品问题 | 确认预期行为、需求和范围 |
| 技术讨论 | 解释方案、依赖和取舍 |
| 代码、PR 与评审 | 请求评审并讨论代码修改 |
| 测试与 Bug | 复现问题，对比实际与预期结果 |
| 演示、发布与生产环境 | 展示功能并讨论部署和生产问题 |
| 意见、决定与跟进 | 同意、反对、建议和确认行动项 |

100 张卡的时态标注统计如下：

| 标注 | 卡片数 |
|---|---:|
| 一般现在时 | 24 |
| 情态动词结构 | 18 |
| 一般现在时 + 现在进行时 | 13 |
| 一般将来时 + 情态动词结构 | 11 |
| 一般现在时 + 情态动词结构 | 10 |
| 一般过去时 | 7 |
| 一般将来时 | 3 |
| 一般现在时 + 一般将来时 | 3 |
| 现在完成时 + 一般过去时 | 3 |
| 一般现在时 + 一般过去时 | 2 |
| 现在完成时 | 2 |
| 其他混合结构 | 4 |

这里统计的是一整张问答卡，所以一张卡可能同时练习两种以上结构。

## 3. 第一级：先搭好句子骨架

### 3.1 主语 + 谓语

用于不需要宾语的动作或事件：

```text
The build failed.
构建失败了。

The dialog opens.
弹框打开。

Testing continues.
测试继续进行。
```

造句时先问两个问题：

1. 这句话在说谁或什么？
2. 它发生了什么？

常见错误：

```text
错误：The build failure.
正确：The build failed.
```

`Failure` 是名词。一个完整句子通常需要 `failed` 这样的谓语动词。

### 3.2 主语 + be + 描述

使用 `be` 描述身份、状态、位置或进度：

```text
The feature is ready.
功能已经准备好了。

The API is backward-compatible.
这个 API 向后兼容。

The issue is in production.
这个问题出现在生产环境。

Testing is in progress.
测试正在进行。
```

`be` 的形式：

| 主语 | 现在 | 过去 |
|---|---|---|
| I | am | was |
| he、she、it、单数名词 | is | was |
| you、we、they、复数名词 | are | were |

常见错误：

```text
错误：The tests is complete.
正确：The tests are complete.
```

### 3.3 主语 + 谓语 + 宾语

当动作作用于某个对象时使用：

```text
We need more information.
我们需要更多信息。

I updated the documentation.
我更新了文档。

QA verified the fix.
QA 验证了这个修复。

The page shows an error message.
页面显示一条错误消息。
```

动词和常用宾语要作为整体学习：

```text
review a pull request       评审 PR
deploy a release            部署版本
reproduce an issue          复现问题
update the documentation    更新文档
meet a deadline             按时完成
raise a concern             提出担忧
```

### 3.4 主语 + 情态动词 + 动词原形

情态动词后面直接使用动词原形：

```text
We can deploy today.
我们今天可以部署。

We should add more logging.
我们应该增加更多日志。

I will review the pull request.
我会评审这个 PR。

The change might affect performance.
这个修改可能影响性能。
```

常见错误：

```text
错误：We should to add more logging.
正确：We should add more logging.

错误：She can reviews it today.
正确：She can review it today.
```

### 3.5 There is / there are

这不是当前 100 句的重点，但在软件沟通中非常实用：

```text
There is an error in the console.
控制台里有一个错误。

There are two open questions.
还有两个未解决的问题。

There was a timeout during deployment.
部署过程中发生了超时。
```

单数或不可数名词使用 `there is`，复数名词使用 `there are`。

### 第一级练习：句子骨架

1. 补全：`The page ___ slow.`
2. 改错：`The tests is complete.`
3. 改错：`I am review the pull request.`
4. 翻译：构建失败了。
5. 翻译：我们需要更多信息。
6. 使用 `can` 翻译：我们今天可以部署。
7. 使用 `There are` 表达“还有两个未解决的问题”。
8. 场景输出：用三个短句分别说明“功能已准备好、QA 正在测试、存在一个阻塞项”。

2. `The tests are complete.` `tests` 是复数。
3. `I review the pull request.` 普通动作句不使用 `am + 动词原形`。
4. `The build failed.`
5. `We need more information.`

7. `There are two open questions.`

## 4. 第二级：把工作放到正确的时间中

### 4.1 一般现在时：事实、状态和可重复行为

公式：

```text
I/You/We/They + 动词原形
He/She/It + 动词-s
```

主要用途：

- 当前事实：`The service depends on Redis.`
- 产品行为：`The page refreshes automatically.`
- 可重复 Bug：`The issue happens when users refresh the page.`
- 表达观点：`I think this approach is simpler.`
- Demo 解说：`I click Save, and the dialog closes.`

否定句和疑问句需要 `do` 或 `does`：

```text
The API does not support pagination.
这个 API 不支持分页。

Does this change affect existing users?
这个修改会影响现有用户吗？

Why does the request fail?
这个请求为什么失败？
```

常见错误：

```text
错误：Why the request fails?
正确：Why does the request fail?
```

### 4.2 现在进行时：正在进行或暂时的工作

公式：

```text
am/is/are + 动词-ing
```

```text
I am investigating the issue.
我正在调查这个问题。

We are testing the fix in staging.
我们正在预发布环境测试这个修复。

The team is working on the migration.
团队正在处理迁移工作。
```

对比：

```text
I test the release every Friday.      每周重复的工作
I am testing the release now.         此刻正在进行
```

表示状态的动词通常不用进行时：

```text
错误：I am understanding the problem.
正确：I understand the problem.
```

### 4.3 一般过去时：已经结束的事件

公式：

```text
主语 + 动词过去式
did not + 动词原形
Did + 主语 + 动词原形 ...?
```

```text
The deployment failed last night.
昨晚的部署失败了。

I reproduced the issue locally.
我在本地复现了这个问题。

We did not change the API contract.
我们没有修改 API 契约。

When did the issue start?
这个问题什么时候开始的？
```

常见错误：

```text
错误：When did it started?
正确：When did it start?
```

`did` 后面使用动词原形。

### 4.4 现在完成时：过去工作与当前结果相连

公式：

```text
have/has + 过去分词
```

```text
We have completed the implementation.
我们已经完成了开发。

Has the fix been tested?
这个修复已经测试过了吗？

I have not reviewed the pull request yet.
我还没有评审这个 PR。
```

当当前结果重要，或者不强调具体过去时间时，使用现在完成时；有明确结束时间时，使用一般过去时：

```text
We have deployed the fix.             强调现在已经部署
We deployed the fix yesterday.        强调昨天发生
```

常用时间标志：

```text
already 已经
yet 还、尚未
just 刚刚
so far 到目前为止
since 自从某个时间点
for 持续一段时间
```

### 4.5 将来表达：计划、承诺和预测

临时决定、承诺或预测使用 `will`：

```text
I will review it today.
我今天会评审它。

The migration will take two days.
迁移需要两天。
```

已有意图或明显迹象使用 `be going to`：

```text
We are going to deploy after lunch.
我们打算午饭后部署。
```

已经安排好的计划可以使用现在进行时：

```text
We are meeting the product team tomorrow.
我们明天要和产品团队开会。
```

截止时间使用 `by`：

```text
We will finish it by Friday.
我们最迟星期五完成。
```

`By Friday` 表示不晚于星期五；`on Friday` 表示事情在星期五当天发生。

### 第二级练习：时间与时态

1. 选择并说明：每天运行测试，使用 `We run` 还是 `We are running`？
2. 翻译：我现在正在调查这个问题。
3. 翻译：部署昨晚失败了。
4. 改错：`When did the issue started?`
5. 翻译：我们已经部署了这个修复。（强调当前结果）
6. 选择并说明：句末有 `yesterday`，使用 `have completed` 还是 `completed`？
7. 翻译：我们会在星期五之前完成它。
8. 场景输出：用三句话说明“昨天完成开发、现在测试、明天部署”。

1. `We run the tests every day.` 重复行为使用一般现在时。
2. `I am investigating the issue now.`
3. `The deployment failed last night.`
4. `When did the issue start?` `did` 后使用动词原形。
5. `We have deployed the fix.`
6. `We completed it yesterday.` 明确结束时间通常使用一般过去时。
7. `We will finish it by Friday.` `by` 表示不晚于该时间。
8. 参考：`We completed the implementation yesterday. We are testing it now. We will deploy it tomorrow.`

## 5. 第三级：提出真正有用的问题

### 5.1 Be 疑问句

把 `be` 移到主语前面：

```text
The feature is ready. → Is the feature ready?
功能准备好了。→ 功能准备好了吗？

Customers are affected. → Are customers affected?
客户受到了影响。→ 客户受到影响了吗？
```

### 5.2 Do/does/did 疑问句

主要动词不是 `be`，句中又没有情态动词时使用：

```text
Does this meet the requirement?
这符合需求吗？

Do we need another review?
我们还需要一次评审吗？

Did the deployment succeed?
部署成功了吗？
```

### 5.3 情态动词疑问句

把情态动词移到主语前面：

```text
Can we deploy today?
我们今天可以部署吗？

Could you review this pull request?
你可以评审一下这个 PR 吗？

Should we add a fallback?
我们应该增加一个降级方案吗？

Will this affect existing users?
这会影响现有用户吗？
```

### 5.4 特殊疑问句

核心公式：

```text
疑问词 + 助动词/情态动词 + 主语 + 主要动词 ...?
```

```text
What does this endpoint return?
这个端点返回什么？

Why did the build fail?
构建为什么失败？

When can we deploy?
我们什么时候可以部署？

How should we handle this case?
我们应该怎样处理这种情况？

Which environment are you using?
你正在使用哪个环境？

Who owns this task?
谁负责这个任务？
```

当疑问词本身就是主语时，不要增加 `do`：

```text
What caused the issue?
什么导致了这个问题？

Who approved the change?
谁批准了这个修改？
```

### 5.5 间接疑问句

间接疑问句语气更加平稳、专业。开头表达后面使用陈述语序：

```text
直接：When will the fix be ready?
修复什么时候准备好？

间接：Could you confirm when the fix will be ready?
你可以确认一下修复什么时候能准备好吗？

直接：Why did the request fail?
请求为什么失败？

间接：Do we know why the request failed?
我们知道请求为什么失败吗？
```

常见错误：

```text
错误：Could you tell me when will it be ready?
正确：Could you tell me when it will be ready?
```

### 第三级练习：提出问题

1. 把 `The feature is ready.` 改为一般疑问句。
2. 把 `This meets the requirement.` 改为一般疑问句。
3. 把 `The deployment succeeded.` 改为一般疑问句。
4. 对原因提问：`The request failed because the token expired.`
5. 翻译：我们什么时候可以部署？
6. 改错：`Why the API is slow?`
7. 改错：`Could you tell me when will it be ready?`
8. 场景输出：针对一个失败的构建，分别询问原因、发生时间和负责人。

<details>
<summary>展开第三级参考答案</summary>

1. `Is the feature ready?`
2. `Does this meet the requirement?` `does` 后使用 `meet`。
3. `Did the deployment succeed?` `did` 后使用 `succeed`。
4. `Why did the request fail?`
5. `When can we deploy?`
6. `Why is the API slow?` `be` 移到主语前。
7. `Could you tell me when it will be ready?` 间接疑问部分使用陈述语序。
8. 参考：`Why did the build fail? When did it fail? Who owns the investigation?`

</details>

## 6. 第四级：请求、能力、建议和确定程度

### 6.1 Can 和 could

```text
Can we move on to the next topic?      许可或可能
我们可以进入下一个议题吗？

Can you share your screen?             直接请求
你可以共享屏幕吗？

Could you repeat that, please?         更委婉的请求
你可以重复一下吗？
```

`Could` 可以让请求更委婉，并不一定表示过去。

### 6.2 Should

`Should` 用于建议、预期行为或推荐的操作：

```text
We should add more logging.
我们应该增加更多日志。

The user should see a clear error message.
用户应该看到清晰的错误消息。
```

### 6.3 Must、have to 和 need to

```text
We must fix the security issue before release.
发布前必须修复这个安全问题。（强制要求）

We have to update the dependency.
我们必须更新这个依赖。（外部条件要求）

We need to confirm the expected behavior.
我们需要确认预期行为。（实际需要）
```

注意下面的区别：

```text
You must not deploy this build.
禁止部署这个构建。

You do not have to deploy today.
今天不必部署。
```

### 6.4 May、might 和 could

用于不确定性和风险：

```text
This may affect performance.
这可能影响性能。

The change might break older clients.
这个修改可能破坏旧客户端。

The timeout could be caused by the database.
超时可能是数据库导致的。
```

可以使用下面的确定程度顺序：

```text
will
一定会

probably will
很可能会

may / might / could
可能会

probably will not
很可能不会

will not
不会
```

### 6.5 Would

用于委婉请求、偏好和假设结果：

```text
Would you mind checking the logs?
你介意检查一下日志吗？

I would prefer the simpler option.
我更倾向于简单的方案。

That would reduce the deployment risk.
那样可以降低部署风险。
```

### 第四级练习：请求、建议与确定程度

1. 使用 `could` 委婉请求对方重复一次。
2. 使用 `should` 建议增加更多日志。
3. 翻译：发布前必须修复这个安全问题。
4. 解释区别：`must not deploy` 和 `do not have to deploy`。
5. 使用 `might` 表达“这个修改可能破坏旧客户端”。
6. 使用 `would prefer` 表达更倾向于简单方案。
7. 改错：`We should to add a fallback.`
8. 场景输出：委婉请求同事今天评审 PR，并说明它可能影响发布。

<details>
<summary>展开第四级参考答案</summary>

1. `Could you repeat that, please?`
2. `We should add more logging.`
3. `We must fix the security issue before release.`
4. `must not deploy` 表示禁止部署；`do not have to deploy` 表示没有必要部署。
5. `The change might break older clients.`
6. `I would prefer the simpler option.`
7. `We should add a fallback.` 情态动词后不加 `to`。
8. 参考：`Could you review the pull request today? It might affect the release.`

</details>

## 7. 第五级：准确描述动作

### 7.1 动词不定式

常见组合：

```text
need to test             需要测试
plan to deploy           计划部署
want to confirm          想确认
ask someone to review    请某人评审
allow users to export    允许用户导出
```

```text
We need to finish testing.
我们需要完成测试。

This allows users to reset their passwords.
这允许用户重置密码。

I asked QA to verify the fix.
我请 QA 验证这个修复。
```

### 7.2 动名词

动名词是像名词一样使用的 `-ing` 形式：

```text
Testing is still in progress.
测试仍在进行。

We discussed adding a cache.
我们讨论了增加缓存。

This prevents users from submitting the form twice.
这可以避免用户重复提交表单。
```

常见组合：

```text
finish testing                   完成测试
avoid breaking                   避免破坏
consider using                   考虑使用
suggest adding                   建议增加
prevent someone from doing       防止某人做某事
```

### 7.3 分词作描述

```text
a breaking change        破坏性修改
the affected users       受影响的用户
the expected result      预期结果
the updated component    更新后的组件
```

`-ing` 通常描述产生影响的事物或主动性质；`-ed` 通常描述受到影响的对象或完成状态：

```text
The behavior is confusing.
这种行为令人困惑。（它让别人困惑）

The user is confused.
用户感到困惑。（用户受到影响）
```

### 第五级练习：准确描述动作

1. 补全：`We need ___ (finish) testing.`
2. 补全：`We discussed ___ (add) a cache.`
3. 改错：`This prevents users to submit twice.`
4. 翻译：我请 QA 验证这个修复。
5. 选择 `confusing` 或 `confused`：`The user is ___.`
6. 场景输出：使用 `plan to`、`consider using` 和 `avoid breaking` 各说一句技术计划。

<details>
<summary>展开第五级参考答案</summary>

1. `We need to finish testing.` `need` 后常接不定式。
2. `We discussed adding a cache.` `discuss` 后接动名词。
3. `This prevents users from submitting twice.` 使用 `prevent someone from doing`。
4. `I asked QA to verify the fix.`
5. `The user is confused.` 用户是受到影响的一方。
6. 参考：`We plan to deploy tonight. We are considering using a cache. We want to avoid breaking older clients.`

</details>

## 8. 第六级：被动语态

> **零基础暂停点：**第一次学习可以先跳过第 8–11 章。能够熟练说出一般现在、正在进行、过去和将来，再回来学习这些结构。

公式：

```text
be + 过去分词
```

当结果、流程或受影响对象比执行者更重要时使用被动语态：

```text
The fix has been tested.
这个修复已经测试过了。

The issue was caused by stale cache data.
这个问题是过期缓存数据导致的。

Only a small number of users are affected.
只有少量用户受到影响。

The release will be deployed tonight.
这个版本今晚会部署。
```

时态体现在 `be` 上：

| 时间 | 主动 | 被动 |
|---|---|---|
| 现在 | QA tests the fix. | The fix is tested. |
| 过去 | QA tested the fix. | The fix was tested. |
| 现在完成 | QA has tested the fix. | The fix has been tested. |
| 将来 | QA will test the fix. | The fix will be tested. |

不要为了显得正式而滥用被动语态。当负责人很重要时，主动语态更清晰：

```text
责任清晰：I will update the API documentation.
我会更新 API 文档。

强调结果：The documentation will be updated before release.
文档会在发布前更新。
```

### 第六级练习：被动语态

1. 改为被动：`QA tested the fix.`
2. 改为被动：`QA has tested the fix.`
3. 改为被动：`The team will deploy the release tonight.`
4. 翻译：只有少量用户受到影响。
5. 选择主动或被动并说明：需要明确谁会更新文档。
6. 场景输出：使用被动语态说明问题原因、修复测试状态和部署时间。

<details>
<summary>展开第六级参考答案</summary>

1. `The fix was tested by QA.`
2. `The fix has been tested by QA.`
3. `The release will be deployed tonight.`
4. `Only a small number of users are affected.`
5. 主动语态更清楚：`I will update the documentation.` 负责人是重要信息。
6. 参考：`The issue was caused by stale cache data. The fix has been tested. It will be deployed tonight.`

</details>

## 9. 第七级：连接多个观点

### 9.1 并列与转折

```text
The implementation is complete, and testing is in progress.
开发已经完成，测试正在进行。

The approach is simple, but it requires a schema change.
这个方案很简单，但它需要修改数据库结构。

The first option is faster, while the second is safer.
第一个方案更快，而第二个方案更安全。
```

### 9.2 原因与结果

```text
We chose this approach because it is easier to maintain.
我们选择这个方案，因为它更容易维护。

The token expired, so the request failed.
令牌过期了，所以请求失败。

Since this is a breaking change, we need a migration plan.
因为这是破坏性修改，所以我们需要迁移计划。

Therefore, I recommend delaying the release.
因此，我建议推迟发布。
```

`because` 后面是原因，`so` 后面是结果。一个因果关系不要同时使用两者：

```text
不自然：Because the token expired, so the request failed.
正确：Because the token expired, the request failed.
正确：The token expired, so the request failed.
```

### 9.3 时间状语从句

```text
When users refresh the page, the session expires.
当用户刷新页面时，会话会过期。

Before we deploy, we need to run the regression tests.
部署前，我们需要运行回归测试。

After the migration finishes, we will verify the data.
迁移完成后，我们会验证数据。

While QA is testing the fix, I will update the documentation.
QA 测试修复时，我会更新文档。
```

表示将来的时间从句，在 `when`、`before`、`after` 后通常使用一般现在时：

```text
错误：When the migration will finish, we will verify the data.
正确：When the migration finishes, we will verify the data.
```

### 9.4 定语从句

定语从句用于识别或补充描述名词：

```text
The component that handles authentication is shared.
处理身份验证的组件是共享组件。

The users who reported the issue are enterprise customers.
报告这个问题的用户是企业客户。

The release, which includes the security fix, is ready.
这个版本已经准备好，其中包含安全修复。
```

- `who` 指人。
- `that` 或 `which` 指事物。
- 逗号表示后面的内容只是额外补充，不用于限定对象。

### 9.5 名词性从句

名词性从句可以作为 `know`、`think`、`confirm`、`explain`、`understand` 的宾语：

```text
We need to confirm what the expected behavior is.
我们需要确认预期行为是什么。

I think that the cache is stale.
我认为缓存已经过期。

Could you explain why this change is necessary?
你能解释一下为什么这个修改是必要的吗？

We do not know whether the issue affects all users.
我们不知道这个问题是否影响所有用户。
```

从句内部使用陈述语序：

```text
错误：We need to confirm what is the expected behavior.
正确：We need to confirm what the expected behavior is.
```

### 第七级练习：连接观点

1. 使用 `but` 连接：方案简单；它需要修改数据库结构。
2. 使用 `because` 连接：我们选择这个方案；它更容易维护。
3. 改错：`Because the token expired, so the request failed.`
4. 补全：`Before we ___ (deploy), we need to run the tests.`
5. 使用定语从句描述“负责身份验证的组件”。
6. 改错：`We need to confirm what is the expected behavior.`
7. 使用 `whether` 表达“不知道问题是否影响所有用户”。
8. 场景输出：用原因、转折和下一步说明一次失败的请求。

<details>
<summary>展开第七级参考答案</summary>

1. `The approach is simple, but it requires a schema change.`
2. `We chose this approach because it is easier to maintain.`
3. `Because the token expired, the request failed.` 或 `The token expired, so the request failed.`
4. `Before we deploy, we need to run the tests.` 将来时间从句使用一般现在时。
5. `The component that handles authentication is shared.`
6. `We need to confirm what the expected behavior is.` 从句内部使用陈述语序。
7. `We do not know whether the issue affects all users.`
8. 参考：`The request failed because the token expired. The API returned 401, but the page showed no message. Therefore, we will add error handling.`

</details>

## 10. 第八级：条件与假设

### 10.1 零条件句：固定系统行为

```text
If the token expires, the API returns 401.
如果令牌过期，API 就返回 401。
```

公式：

```text
if + 一般现在时，一般现在时
```

用于系统行为、规则和可重复的结果。

### 10.2 第一条件句：真实的将来可能

```text
If the tests pass, we will deploy tonight.
如果测试通过，我们今晚就部署。

If it fails again, we can roll back the release.
如果再次失败，我们可以回滚版本。
```

公式：

```text
if + 一般现在时，will/can/may + 动词原形
```

`if` 从句中通常不使用 `will`：

```text
错误：If the tests will pass, we will deploy.
正确：If the tests pass, we will deploy.
```

### 10.3 第二条件句：假设的设计选择

```text
If we moved this logic to the backend, the client would be simpler.
如果我们把这个逻辑移到后端，客户端会更简单。

If we had more time, I would add integration tests.
如果有更多时间，我会增加集成测试。
```

公式：

```text
if + 一般过去时，would + 动词原形
```

这个结构特别适合架构和方案取舍讨论。

### 10.4 Unless 和 otherwise

```text
We cannot release unless the critical tests pass.
除非关键测试通过，否则我们不能发布。

We need to update the schema; otherwise, the migration will fail.
我们需要更新数据库结构，否则迁移会失败。
```

`Unless` 相当于 `if not`。

### 第八级练习：条件与假设

1. 描述固定行为：令牌过期时，API 返回 401。
2. 描述真实计划：如果测试通过，我们今晚部署。
3. 改错：`If the tests will pass, we will deploy.`
4. 描述假设选择：如果把逻辑移到后端，客户端会更简单。
5. 使用 `unless` 表达“除非关键测试通过，否则不能发布”。
6. 使用 `otherwise` 表达“需要更新结构，否则迁移会失败”。

<details>
<summary>展开第八级参考答案</summary>

1. `If the token expires, the API returns 401.`
2. `If the tests pass, we will deploy tonight.`
3. `If the tests pass, we will deploy.` `if` 从句通常不用 `will`。
4. `If we moved the logic to the backend, the client would be simpler.`
5. `We cannot release unless the critical tests pass.`
6. `We need to update the schema; otherwise, the migration will fail.`

</details>

## 11. 第九级：比较方案与表达观点

### 11.1 比较级

```text
This approach is simpler.
这个方案更简单。

The cached version is faster than the original version.
缓存版本比原版本更快。

Option A is more flexible but less predictable.
A 方案更灵活，但可预测性更低。
```

常见形式：

```text
fast → faster                 更快
simple → simpler             更简单
easy → easier                更容易
reliable → more reliable     更可靠
complex → less complex       不那么复杂
```

### 11.2 平衡地说明取舍

```text
Option A is faster, but it uses more memory.
A 方案更快，但占用更多内存。

Option B is easier to maintain, although it requires more initial work.
B 方案更容易维护，尽管前期工作更多。

The benefit is lower latency; the trade-off is additional complexity.
好处是延迟更低，代价是复杂度增加。
```

### 11.3 同意与不同意

```text
I agree with that approach.
我同意这个方案。

That makes sense to me.
我认为这有道理。

I agree with the goal, but I am concerned about the timeline.
我认同目标，但我担心时间安排。

I see your point. However, this may affect backward compatibility.
我理解你的观点。不过，这可能影响向后兼容性。

I would recommend a smaller change first.
我建议先做一个更小的修改。
```

讨论不确定的决定时，优先使用 `I think`、`I suggest`、`I recommend`、`I am concerned`，避免没有依据的绝对表达。

### 第九级练习：比较与表达观点

1. 写出 `fast`、`easy` 和 `reliable` 的比较级。
2. 使用 `than` 表达“缓存版本比原版本更快”。
3. 使用 `but` 说明“A 方案更快，但使用更多内存”。
4. 翻译：好处是延迟更低，代价是复杂度增加。
5. 委婉表达：认同目标，但担心时间安排。
6. 场景输出：比较两个方案，从速度、维护成本和风险三个方面推荐一个。

<details>
<summary>展开第九级参考答案</summary>

1. `faster`、`easier`、`more reliable`。
2. `The cached version is faster than the original version.`
3. `Option A is faster, but it uses more memory.`
4. `The benefit is lower latency; the trade-off is additional complexity.`
5. `I agree with the goal, but I am concerned about the timeline.`
6. 参考：`Option A is faster, but it is harder to maintain. Option B is more reliable and has lower deployment risk. I recommend Option B.`

</details>

## 12. 第十级：组成完整的软件工作表达

### 12.1 Demo 表达链

```text
背景 Context → 目标 Goal → 操作 Action → 结果 Result → 价值 Value → 过渡 Transition
```

```text
This is the user management page.
这是用户管理页面。

It allows administrators to manage team members.
它允许管理员管理团队成员。

First, I click Add user.
首先，我点击 Add user。

A dialog opens, and I enter the user's details.
弹框打开，我输入用户信息。

After I click Save, the new user appears in the table.
点击 Save 后，新用户会出现在表格中。

This reduces the number of steps required to onboard a teammate.
这减少了添加新成员所需的步骤。

Next, let's look at filtering.
接下来，我们来看筛选功能。
```

核心语法：

- 使用一般现在时描述可见行为。
- 使用 `can` 和 `allow someone to` 描述能力。
- 使用时间从句说明操作与结果。
- 使用连接词组织步骤。

### 12.2 Bug 表达链

```text
问题 Problem → 步骤 Steps → 实际 Actual → 预期 Expected → 影响 Impact → 下一步 Next step
```

```text
Users cannot submit the form after their session expires.
会话过期后，用户无法提交表单。

The issue happens when they leave the page open for more than an hour.
当页面打开超过一小时时，这个问题就会发生。

When they click Submit, the API returns 401, but the page shows no message.
点击 Submit 时，API 返回 401，但页面没有显示消息。

The page should ask them to sign in again.
页面应该提示他们重新登录。

This blocks users from completing the workflow.
这会阻止用户完成流程。

I am adding error handling, and QA will test the fix this afternoon.
我正在增加错误处理，QA 会在今天下午测试这个修复。
```

核心语法：

- 使用一般现在时描述可重复行为。
- 使用 `when` 表示复现条件。
- 使用 `should` 描述预期行为。
- 使用现在进行时和将来时描述修复计划。

### 12.3 进度表达链

```text
已完成 Completed → 当前 Current → 阻塞 Blocker → 时间 ETA → 下一步 Next step
```

```text
I have completed the implementation.
我已经完成了开发。

I am testing the migration in staging now.
我正在预发布环境测试迁移。

The only blocker is access to the production snapshot.
唯一的阻塞项是生产快照的访问权限。

If I get access today, I will finish by Thursday.
如果今天获得权限，我会在星期四之前完成。

After that, I will open the pull request.
之后，我会创建 PR。
```

### 12.4 技术决策表达链

```text
建议 Recommendation → 原因 Reason → 取舍 Trade-off → 风险 Risk → 缓解 Mitigation
```

```text
I recommend using the existing authentication service.
我建议使用现有的身份验证服务。

The main reason is that it already supports token refresh.
主要原因是它已经支持令牌刷新。

It is easier to integrate, but we will have less control over caching.
它更容易集成，但我们对缓存的控制会更少。

The biggest risk is additional latency.
最大的风险是额外延迟。

We can mitigate that by caching the public keys locally.
我们可以通过在本地缓存公钥来降低这个风险。
```

## 14. 替换练习法

选择一个句子骨架，每次替换一个位置：

```text
Could you review [the pull request] by [Friday]?
你可以在星期五之前评审这个 PR 吗？

Could you review [the API design] by [tomorrow morning]?
你可以在明天上午之前评审 API 设计吗？

Could you review [the migration plan] before [the meeting]?
你可以在会议前评审迁移计划吗？
```

然后保持内容不变，修改语法：

```text
I review the pull request every morning.         日常习惯
I am reviewing the pull request now.             正在进行
I reviewed the pull request yesterday.           过去完成
I have reviewed the pull request.                强调当前结果
I will review the pull request after lunch.      将来动作
```

最后连接成完整表达：

```text
I have reviewed the pull request. The implementation looks good, but I found one backward-compatibility issue. If we fix that issue, we can merge it today.

我已经评审了这个 PR。实现看起来不错，但我发现了一个向后兼容问题。如果解决这个问题，我们今天就可以合并。
```

## 15. 中文母语者常见错误

### 缺少谓语动词

```text
错误：The feature very useful.
正确：The feature is very useful.
```

### 第三人称单数缺少 `-s`

```text
错误：The page show an error.
正确：The page shows an error.
```

### 重复使用过去式

```text
错误：Did the build failed?
正确：Did the build fail?
```

### 疑问句语序错误

```text
错误：Why the API is slow?
正确：Why is the API slow?
```

### 把形容词当动词

```text
错误：We need compatible the old API.
正确：We need to keep the old API compatible.
```

### 混淆 finish 和 finished

```text
I finished the task.       finish 是过去式谓语
The task is finished.      finished 描述完成状态
```

### 把所有“有”翻译成 have

```text
错误：The console has an error.
更自然：There is an error in the console.
```

### 过度使用长句

```text
风险较高：Because the deployment failed and users could not log in so we rolled back and now we are checking the logs.

更清楚：The deployment failed, and users could not log in. We rolled it back. We are checking the logs now.

部署失败了，用户无法登录。我们回滚了版本，现在正在检查日志。
```

## 18. 毕业标准

满足下面五个条件，才算真正学会一个句型：

1. 不逐字翻译也能理解。
2. 看到中文后 3 秒内能够说出英文主干。
3. 能够正确替换至少三个内容位置。
4. 能够把它改成疑问、否定、过去或将来形式。
5. 能够把它和另外两个句子组成真实的软件工作表达。

最后使用下面五项能力检查实际水平：

- 完成一次 60 秒功能 Demo。
- 完成一次 45 秒进度同步。
- 从复现步骤到下一步完整解释一个 Bug。
- 比较两个技术方案并推荐其中一个。
- 回答一个没有提前准备的追问。

短而准确的句子是基础。只有当复杂结构能让观点之间的关系更清楚时，才需要增加复杂度。
